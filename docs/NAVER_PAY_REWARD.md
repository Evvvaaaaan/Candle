# 10연승 리워드와 네이버페이 지급 인수 안내

확인일: 2026-10-11. 이 문서는 **프론트 구현과 지급 제안 계약**입니다. 실제 네이버페이 제휴 계약, 지급 API, 당첨 판정 또는 세무 처리가 완료되었다는 의미가 아닙니다.

## 1. 공식 자료에서 확인한 내용

| 근거 | 확인 내용 | 화면/서버에 반영한 내용 |
|---|---|---|
| [네이버페이 포인트 제휴](https://npayad.naver.com/point) | 기업 지급에는 ID 적립과 쿠폰 전달 방식이 있다. | 운영자가 계약한 `method`에 따라 입력 항목 전환. 사용자 임의 선택은 제공하지 않음 |
| [공식 포인트 소개서](https://npayad.naver.com/api/files/202406-281549585/NAVERPAY_POINT.pdf), ‘포인트 지급 방법’ | ID 방식은 고객 네이버 ID 및 적립내역 전달, 개인정보 제3자 제공 동의가 필요하다. 쿠폰은 기업이 문자/푸시 등으로 전달한다. | ID 직접 적립에는 `naverId`, 수집·이용 및 제3자 제공 동의. 문자 쿠폰에는 수신 `phone` |
| 같은 소개서의 지급 방법·FAQ | 네이버페이 약관에 동의한 계정이어야 적립·사용할 수 있다. | 본인 계정/이용약관 확인 항목. 실제 계정 상태 확인은 서버/지급 제공자가 수행 |
| [국세청 기타소득 원천징수 안내](https://d.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=7893&mi=6457) | 기타소득의 과세 여부·원천징수는 소득 종류와 필요경비 등에 따라 판단한다. | 100만원 경품에 임의로 세율을 적용하지 않음. 승인된 `taxNotice`와 실제 `payoutPoints`를 서버에서 수신 |

공식 PDF는 URL상 2024 배포 파일이나 본문 표기는 **2023.01**이다. 지급 방식의 근거로 활용했으며, 보유 한도·지급 한도·유효기간·수수료·정산일을 최신 확정 조건으로 사용하지 않았다. 특히 100만원을 한 번에 지급할 수 있는지, 대상 계정의 한도, 쿠폰 권종과 분할 발송은 계약 담당자에게 확인해야 한다. 공개 소개서는 파일 전달 방식도 설명하므로, 네이버에 공개 지급 REST API가 있다고 가정하지 않는다. 아래 API는 **Candle 자체 백엔드용**이다.

## 2. 실제 사용자 화면

홈 10연승 배너에서 챌린지 안내를 연 뒤 ‘당첨 확인 · 리워드 수령’을 선택한다. 내 정보의 ‘10연승 리워드’에서도 같은 `#challenge-reward` 화면으로 들어간다.

기존 정책인 **10연승 달성자 중 추첨**을 유지한다. 10연승만으로 당첨/지급 완료를 표시하거나, 일반 포인트 교환 잔액을 차감하지 않는다. 서버의 수령 상태만 표시한다.

| 상태 | 화면 동작 |
|---|---|
| `NOT_ELIGIBLE` | 대상 아님 안내, 입력 폼 없음 |
| `AWAITING_DRAW` | 10연승 달성 및 추첨 대기 안내, 입력 폼 없음 |
| `ELIGIBLE` | 당첨 안내, 지급 포인트·신청 기한·세금 안내·수령 입력·버전별 필수 동의 |
| `REQUESTED` | 신청 접수와 접수 번호. 지급 완료 문구 사용 안 함 |
| `PROCESSING` | 지급 처리 중 |
| `PAID` | 제공자 지급 결과 확인 후 완료 표시 |
| `REJECTED` | 서버의 승인된 `statusNote`로 사유/후속 절차 안내 |
| `EXPIRED` | 신청 기한 종료 안내 |

입력 폼이 없는 상태 안내에는 새로고침을 제공한다. API 404/503은 준비 중과 재시도, 401은 로그인 복귀로 처리한다. 기한은 서버 시각에 경과 시간을 더해 검사하지만 최종 판정은 서버가 한다. 새로고침/화면 이탈 시 입력 원문은 사라진다.

로컬 미리보기는 **가상의 당첨 예제**로 폼을 보여주며 실제 당첨·지급이 아니라는 안내를 붙인다. 개발용 계약 서버도 같은 예제만 사용한다. 운영 빌드에는 해당 로컬 어댑터가 포함되지 않는다.

## 3. 필요한 수령 정보

| 항목 | ID 직접 적립 (`NAVER_ID`) | 문자 쿠폰 (`COUPON_SMS`) |
|---|---|---|
| 입력 정보 | 네이버 로그인 ID. 닉네임과 구별 | 본인 휴대폰 번호, 현재 국내 010 번호 지원 |
| 오입력 방지 | 동일 ID 재입력 | 동일 번호 재입력, 하이픈 제거 후 비교 |
| 수집·이용 동의 | `collection` 필수 | `collection` 필수 |
| 제3자 제공 동의 | `provision` 필수 | 실제 지급 사업자/위탁 구조에 맞는 승인 항목을 서버에서 제공 |
| 계정 확인 | 본인 계정 및 네이버페이 약관 동의 확인 | 쿠폰 등록에 사용할 본인 계정 및 네이버페이 약관 동의 확인 |

이름, 주소, 계좌번호, 주민등록번호, 신분증, 네이버 비밀번호는 이 지급 폼에서 받지 않는다. 이름/고유식별정보 등이 세무 신고에 필요한지는 세무 검토 후 결정하고, 필요하다면 법적 근거·처리 주체·암호화·보관 기간이 확정된 별도 보안 절차에서 처리한다. 해당 절차가 완료되어야 신청 가능하다면 서버는 그 전까지 `ELIGIBLE`을 반환하지 않아야 한다.

네이버 로그인으로 받은 서비스별 사용자 식별자는 지급용 네이버 로그인 ID와 동일하다고 가정하지 않는다. 사용자의 확인 체크는 실제 명의/계정 인증을 대신하지 않는다. 서버에서 본인성, 계정 존재·이용 가능 여부, 오입력 처리 및 정정 절차를 검증해야 한다.

## 4. 백엔드 계약

정확한 스키마는 [openapi.json](openapi.json)의 `ChallengeReward`, `ChallengeRewardRequest`를 따른다. 접두사는 `/api/v1`이다.

### GET `/challenges/ten-wins/reward`

수령 화면 진입 시 별도로 조회한다. 앱 초기 7개 데이터 조회에는 추가하지 않아 이 API 미구현이 다른 화면을 막지 않는다.

- `status`: 위 상태 중 하나. 클라이언트 기록을 보고 판정하지 않는다.
- `awardId`: 서버가 현재 회원에게 발급한 당첨 건 ID. 대상이 없으면 `null`.
- `claimId`: 신청 전 `null`, 접수·처리 중·지급 완료에는 실제 접수 번호 필수.
- `amount`: 이번 캠페인 리워드 액면 `1000000`.
- `payoutPoints`: 세무/운영 정책을 반영한 실제 지급 포인트. 정수 1~1,000,000.
- `method`: `NAVER_ID` 또는 `COUPON_SMS`. 서버에서 지급 계약에 따라 고정.
- `serverTime`, `claimDeadline`: 타임존이 있는 ISO 시각. 신청 대상이 아니면 기한은 `null` 가능.
- `taxNotice`: 세금 부담 주체, 공제/별도 납부 여부와 실수령액의 승인된 안내. 미확정 상태로 운영 폼을 열지 않는다.
- `deliveryNotice`: 지급 예정, 처리 기간, 실패 문의/정정 방법 등 실제 운영 안내.
- `statusNote`: 현재 상태의 안내. 내부 오류나 개인정보를 포함하지 않는다.
- `agreements`: `{id,title,version,body}` 목록. ID는 `collection`/`provision`. 제공받는 자, 목적, 항목, 보유 기간, 거부 권리 및 영향 등을 운영 주체가 검토한 일반 텍스트로 제공한다. HTML은 렌더링하지 않는다.

`ELIGIBLE`에는 당첨 ID, 기한, 수집 동의가 필요하고 ID 적립에는 제3자 제공 동의도 필수다. 부족하거나 잘못된 응답이면 폼을 열지 않는다. 미계약/정책 준비 중에는 503을 반환한다.

### POST `/challenges/ten-wins/claims`

```json
{
  "awardId": "award-server-id",
  "method": "NAVER_ID",
  "recipient": { "naverId": "example_login_id" },
  "agreements": [
    { "id": "collection", "version": "approved-version", "accepted": true },
    { "id": "provision", "version": "approved-version", "accepted": true }
  ],
  "npayTermsConfirmed": true
}
```

쿠폰 방식은 `recipient: {"phone":"01012345678"}`을 사용하며 ID와 전화번호를 함께 보내지 않는다. 금액/회원 ID/당첨 상태는 클라이언트에서 보내지 않는다. 성공은 `{ "id": "claim-server-id" }`이며, 이후 GET 조회가 `REQUESTED` 등 최신 상태를 반환해야 한다.

서버 필수 처리:

1. 세션·CSRF·Origin, 회원별 당첨 건 소유권, 추첨 확정, 신청 기한, 세무/본인 확인 선행 조건을 재검증한다.
2. 서버에 저장된 지급 방식, 수령 정보 형식, 약관 버전과 필수 동의를 확인한다. `npayTermsConfirmed`만으로 계정 검증을 생략하지 않는다.
3. 당첨 건당 단일 신청 고유 제약을 두고 원자적으로 접수한다. 일반 앱 포인트 원장을 차감하지 않는다.
4. `Idempotency-Key`로 중복 처리한다. 동일 키와 동일 본문에는 기존 ID를 반환하고, 본문 변경은 `IDEMPOTENCY_CONFLICT`로 거부한다. 결과가 불확실한 재시도에서 프론트는 같은 키를 유지한다.
5. 프론트 저장소의 재시도 식별에는 회원/작업/당첨 ID만 남긴다. 수령 원문은 저장·로그·분석 이벤트에 포함하지 않는다. 서버도 지급 데이터 접근/보관 정책을 적용한다.
6. 제공자 응답/배치 정산을 확인한 후에만 `PAID`로 변경한다. 접수 성공을 지급 성공으로 바꾸지 않는다. 쿠폰 발행·전달·등록 중 무엇을 `PAID`로 볼지 계약과 안내에서 정의한다.

주요 오류: `REWARD_NOT_ELIGIBLE`(403), `REWARD_EXPIRED`(409), `ALREADY_CLAIMED`(409), `RECIPIENT_INVALID`(400), `AGREEMENT_REQUIRED`(400), `IDEMPOTENCY_CONFLICT`(409), `SESSION_EXPIRED`(401). 이미 접수된 건은 GET에서 기존 내역을 보여준다.

## 5. 출시 전 필요한 결정

- 기존 추첨 방식의 회차·달성 판정·당첨 인원·중복 당첨 및 지급 정책.
- 네이버페이/공급사 계약, 실제 ID 적립 또는 문자 쿠폰 방식, 100만원 지급 가능 조건과 처리 일정.
- 100만원의 세전/세후 의미, 제세공과금 부담 주체, 본인확인 및 세무 신고 담당자/절차.
- 승인된 수집·이용/제3자 제공 동의문, 제공받는 자·항목·보유 기간, 고객 문의 및 정정 창구.
- 실제 계정으로 적립/발송 성공, 계정 오류, 한도 초과, 중복·실패·재처리 검증.

## 6. 검증

`npm run check`는 기존 앱 검사와 새 리워드 검사 모두 실행한다. 새 검사는 운영 산출물에서 홈부터 수령 신청까지 이동하고, 필수 입력/동의, 수령 정보 재입력, 네트워크 재시도 키, 브라우저 개인정보 비저장, 잔액 무차감, 새로고침, 전체 상태, 쿠폰 전환, 기한 만료, 503 재시도, 401과 320/390/1440px 레이아웃을 확인한다.

실제 네이버페이 적립, 세무 신고, Safari와 모바일 실기기는 자동 검증에 포함되지 않는다.
