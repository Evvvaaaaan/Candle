# Candle 프론트 출시 준비 계획

## 조사 기준

2026-10-11, `Candle`의 Core Flow와 로컬 `Candle-backend` 소스를 직접 확인했다. 최초 조사 당시 최신 화면은 Git에 추가되지 않았으며 기존 API 서비스와 연결되지 않았다. 로그인 버튼은 약관 화면 이동만 수행했고 지급 신청은 서버 요청 없이 성공 안내를 표시했다. 포인트, 통계, 교환 기록이 고정값이며 출석과 결과 수령은 새로고침하면 초기화됐다. 약관 보기와 프로필 메뉴 일부는 안내 메시지만 표시했다.

백엔드에서 확인한 구현은 `GET /api/v1/stocks/top-list`, `GET /api/v1/stocks/{ticker}`, `GET /api/v1/stocks/logo/{ticker}`이다. 인증·지급·예측 API 구현과 운영 주소, 광고/지급 사업자 계약은 이 저장소에서 확인되지 않았다. 따라서 프론트의 연동 준비 완료와 실제 서비스 출시 승인을 구분한다.

## 완료 기준과 검증

1. 현재 Core Flow를 단일 앱 진입점으로 유지한다. 로그인 위치 및 홈 더보기 제거를 유지하고 모든 화면을 모바일/데스크톱에서 검증한다.
2. 같은 화면에서 데모와 API 어댑터를 사용한다. 운영 호스트는 기본 API 모드이며 API 실패를 가짜 성공이나 데모 데이터로 대체하지 않는다.
3. 서버 세션, 약관 버전, 인증 만료, 예측 마감, 서버 잔액을 사용한다. 지급·보상·예측은 성공 응답 후 갱신하고 중복 클릭/재시도는 멱등 키를 사용한다.
4. 로딩·오류·빈 결과·재시도·접근성 상태를 제공한다. 서버 문자열은 HTML로 실행되지 않아야 한다. 개인정보·인증 토큰을 로컬 저장하지 않는다.
5. 데모도 출석·수령·교환 후 상태가 일관되고 새로고침 후 유지되도록 한다. 데모 광고 타이머는 실제 광고 보상으로 사용하지 않는다.
6. 기존 종목 API와 일치하는 어댑터, 새 API의 OpenAPI 계약, 로컬 계약 서버, 재현 가능한 자동 테스트와 CI를 제공한다.
7. 정적 배포 산출물에 구형 데모 페이지·테스트·개발 파일이 섞이지 않게 하고 연동/배포/운영 점검 절차를 문서화한다.
8. 변경을 검토하고 비밀정보를 점검한 뒤 `origin/main`에 일반 push한다. 원격 커밋 일치 여부를 확인한다.

## 반복 점검 기록

- 기준 단위 테스트: 예측권 원장 12개 통과.
- 최초 브라우저 실행: `net::ERR_CONNECTION_REFUSED`로 실패. 미리보기 서버 재시작 후 17개 화면·10가지 크기 및 기존 기능 검사 211개를 통과했으나 `/favicon.ico` 404로 최종 검사 실패. 명시적인 파비콘을 추가했다.
- 데모/실제 API의 공통 화면, 쿠키 세션·CSRF·버전별 약관·멱등 키를 구현했다. 가짜 지급 성공과 고정 잔액을 제거하고, 실패 시 입력 유지·재시도·인증 화면 복귀를 검증했다.
- 출석·결과 수령·예측/광고 미션·교환의 데모 원장을 한 저장 항목에 기록하고 탭 간 쓰기를 직렬화했다. 새로고침 후 잔액과 내역, 중복 처리, 개인정보 원문 미저장을 검사했다.
- 기존 API에 없는 차트·참여 비율·실제 지급 조건·고정 통계·기능 없는 메뉴는 운영 화면에서 제공하지 않는다. 고객 문의/계정 삭제/푸시 알림/실제 리워드 정책은 아래 출시 의존성을 충족한 뒤 노출해야 한다.
- ‘이전 내역 더 보기’ 요청이 401을 받으면 잔액이 화면에 남는 문제를 실제 브라우저에서 재현했다. 세션 만료 처리를 공통화하여 초기 로딩·변경 요청·페이지네이션 모두 보호 정보를 비우고 로그인으로 복귀하도록 수정했다.
- 최종 `npm run check` 통과: 코드 포맷 검사, 단위/계약 테스트 **28개**, 운영 빌드, 브라우저 검사 **254개**, JavaScript 오류 **0개**. 브라우저 검사는 21개 화면을 320×568부터 1440×1000까지 10가지 크기로 검사하며, 버튼 접근성·광고 완료·지급 재시도·약관 조회 후 입력 유지·인증 만료·빈 결과·문자열 주입·이전 내역 조회를 포함한다.
- `dist/`를 직접 서비스한 API 모드의 로그인/동의/홈 진입을 확인했고, 데모 어댑터·구형 화면·개발 서버·Git 파일이 제공되지 않는 것을 검사했다. 외부 Spring/OAuth/광고/지급 서버가 아닌 로컬 계약 시뮬레이터로 검증했다.
- 검증 결과: [검사 목록](verification.json), [모바일 홈](screenshots/home-mobile.png), [로그인 화면](screenshots/signup-desktop.png). CI는 GitHub Actions의 같은 `npm run check` 절차를 사용한다.
- GitHub Actions의 첫 실행도 통과했다. 실행 로그의 구형 Action 런타임 지원 중단 경고와 `ubuntu-latest` 전환 안내를 확인하여 공식 Actions 릴리스 및 `ubuntu-24.04`로 고정했다. 재실행 결과는 저장소 Actions 탭에서 해당 커밋과 함께 확인할 수 있다.

## 사용자 화면 전환 검증 (2026-10-11)

- 시작 기준: 단위·계약 28개, 브라우저 254개 검사 통과.
- 모든 실행 모드에서 화면 선택 패널을 제거하고, 로그인 상태에 따라 기본 진입 화면을 결정한다. 신규 방문은 로그인, 가입한 사용자의 재방문은 홈이다.
- 21개 화면을 `src/js/screens/`의 개별 모듈로 분리했다. API·이벤트 처리는 기존 공통 컨트롤러를 유지하며 운영 빌드에 화면 모듈을 포함한다.
- 사용자 화면의 DEMO/데모 문구를 제거했다. 기존 로컬 회원명·원장 제목은 잔액과 내역을 유지하면서 정리한다. 로컬 기록 저장 키와 내부 어댑터 식별자는 호환을 위해 유지한다.
- 상승 아이콘은 진한 빨강 화살표와 거의 같은 빨강 배경 때문에 식별이 어려웠다. 배경·선택 테두리를 연하게 바꾸고 브라우저에서 화살표 대비가 3:1 이상임을 확인했다. 하락 선택도 같은 톤으로 맞췄다.
- 휴대폰 모형 프레임을 제거하고 최대 480px의 모바일 앱 레이아웃을 사용한다. 가상 차트를 제거한 종목 카드의 고정 높이도 없애고 실제 표시 내용에 맞췄다. 로그인 하단 배치와 홈의 더보기 버튼 제거를 유지했다.
- 최종 `npm run check`: 단위·계약 **29개**, 브라우저 **468개**, JavaScript 오류 **0개**, 포맷·운영 빌드 통과. 기존 이용 흐름과 오류 복구에 더해 첫 방문/재방문, 화면별 개발 문구·메뉴 부재, 화살표 대비, 기존 기록 호환을 검사했다.

## 실제 출시 승인에 필요한 외부 작업

- 명세의 인증·약관·예측·포인트·광고·교환 API를 서버에 구현하고 스테이징에서 검증.
- 로그인 제공자별 앱 등록/redirect URI, 서버 세션 쿠키와 CSRF 설정.
- 광고 사업자 완료 콜백과 지급 사업자 정산/실패/중복 처리.
- 운영자가 승인한 약관/개인정보/리워드 정책, 실제 거래일·마감·보합 처리.
- 실제 계정과 테스트 지급수단을 이용한 스테이징 종단 간 검증 및 배포 승인.
- 고객 문의·개인정보 삭제/탈퇴 처리 창구, 푸시 알림 범위와 앱스토어 제출 요구사항 확정. 현재 프론트의 계정 설정에는 약관과 로그아웃만 제공한다.

## 전달 상태의 해석

프론트 개선·API 계약·로컬 자동 검증은 완료되었다. 실제 서비스의 출시 승인은 위 외부 작업과 스테이징/실기기 검증 완료 후에 가능하다. 운영 백엔드 미구현 기능을 연결 완료로 표현하거나 계약 시뮬레이터 결과를 실서버 검증으로 대체하지 않는다.
